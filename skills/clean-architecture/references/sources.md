Retrieved 2026-11-22 via Firecrawl (`firecrawl_scrape`). Statements below summarize the canonical sources and separate architectural rules from author claims.

| # | Source | What the skill takes from it |
|---|---|---|
| 1 | Robert C. Martin (Uncle Bob), "The Clean Architecture" (2012-08-13), https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html | Synthesis of Hexagonal, Onion, Screaming, DCI, and BCE architectures; the five properties (Independent of Frameworks, Testable, Independent of UI, Independent of Database, Independent of any external agency); the four concentric circles (Entities, Use Cases, Interface Adapters, Frameworks & Drivers); **The Dependency Rule** (source code dependencies point inward only); crossing boundaries via Dependency Inversion (Input/Output Ports, Interactors, Presenters); passing simple, inner-convenient data structures across boundaries. |
| 2 | Marco Tulio Valente, *Software Engineering: A Modern Approach*, "Building Software with a Clean Architecture", https://softengbook.org/articles/clean-architecture | Detailed walkthrough of Entities (enterprise-wide rules), Use Cases (application-specific domain operations), Adapters (mediating REST/DB with Use Cases), and External Frameworks; explanation of how the Dependency Rule reverses the traditional layered dependency on persistence via Inversion of Control and interfaces owned by the Use Case layer. |
| 3 | Jason Taylor, `CleanArchitecture` Solution Template for ASP.NET Core, https://github.com/jasontaylordev/cleanarchitecture | Production project layout mapping the concentric circles to four concrete projects/modules: `Domain` (Entities, Value Objects, Domain Events — zero dependencies), `Application` (Use Cases / Commands & Queries, interfaces — depends only on `Domain`), `Infrastructure` (EF Core / DB / external services implementing `Application` interfaces), and `Web` (Presentation / composition root); functional, integration, application, and domain unit test separation. |
| 4 | Microsoft .NET Architecture Guide, "Common web application architectures — Clean Architecture", https://learn.microsoft.com/pt-pt/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures#clean-architecture | Diagram and rules for Application Core (`Entities` + `Interfaces` + `Use Cases/Services`), `Infrastructure` (Repositories, EF Core, external APIs), and `UI/Web` depending inward on Application Core; contrast with database-centric N-Layer dependencies. |

## Notes on disagreements and nuances across sources

- **Strict Presenter/Output Port vs. MediatR/Command-Handler return values:** Uncle Bob's 2012 diagram (Source 1) shows control flowing `Controller -> Input Port -> Use Case Interactor -> Output Port -> Presenter`. Pragmatic templates like Jason Taylor's (Source 3) and Microsoft's guide (Source 4) often let a Command/Query handler in `Application` return a Response DTO directly to the Controller while still strictly enforcing the inward Dependency Rule for all persistence and external services. Both are valid as long as inner circles never import outer circles.
